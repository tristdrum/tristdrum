# Airbnb browser pilot

Read-only, fail-closed host-website evidence code for Bougainvillea, Spekboom and Jasmine. **Do not deploy, log in through, or schedule this browser pilot under the current Airbnb Terms.** No cloud deployment/login, Airbnb write, guest message, or real guest fixture was made for this branch.

## Terms hold

[Airbnb Terms section 11.1](https://www.airbnb.com/help/article/2908) prohibits bots, scrapers and other automated means of accessing or interacting with its platform. The bespoke browser pilot has **no separately documented Airbnb permission**. User or host approval alone does not satisfy that requirement. `server.mjs` now checks `runtime-authorization.mjs` **before loading config, opening a listener, or starting 5-minute/15-minute polling**. Its code-pinned Airbnb grant is `null`, so the real server cannot start. No environment variable or Fly secret can enable it. A future change would require independent review of an Airbnb-issued written grant covering this exact automated calendar-and-messages use, a code-reviewed pin of its SHA-256 and expiry, and its private owner-only document mounted at runtime. The hash check is an interlock, not independent proof of the document's provenance; the written permission and scope still require human verification. This task does not make that future change.

The reviewed grant must pin `expiresAt` as an exact ISO instant with `Z` or an explicit offset. Date-only values and timestamps without a zone are rejected. For an end-of-day SAST grant, use `+02:00`; the runtime will not assume that the SAST date ends at midnight UTC.

Alternatives to evaluate separately are [Airbnb's official iCal calendar export](https://www.airbnb.com/help/article/99) for availability-only evidence, or an [Airbnb-connected software provider](https://www.airbnb.com/help/article/2346) / authorized [API program](https://www.airbnb.com/help/article/3418) for richer integration. iCal does not provide the exact reservation/message fields this pilot sought, and neither route is automatically authorized for this bespoke service.

## Observed UI and limits

Read-only inspection of the existing signed-in personal browser on 2026-09-24 established the `.co.za` host routes and DOM shape, without copying cookies or guest content to the repo or cloud:

- Calendars use `https://www.airbnb.co.za/multicalendar/<listingId>`. Three simultaneous `div[role="grid"][aria-label="Month YYYY"]` grids contain `button[data-date]` inside day cells. `div[data-testid="reservation-bar"]` is inside a clickable row, not an anchor. A bar opens `/multicalendar/<listingId>/reservation/<code>`, with a labelled confirmation code, `guestFirstName`, and a visible `/users/profile/<id>` guest link.
- The parser requires each grid's full month and the current SAST month. A day may describe two adjacent bookings; all `Checkin on ..., checkout on ...` intervals are collected and overlapping/malformed pairs fail. A labeled bar must have a recognized selector and parseable interval. An empty decorative bar is ignored **only** when a nonempty bar has the exact same selector; an unmatched empty bar fails. Labeled-bar intervals must exactly match the distinct intervals described by reserved days, and **every** labeled bar (up to 80 per listing) must yield the same complete detail for its interval, with route/visible-code agreement. Unknown, extra, missing or conflicting bars fail the snapshot. `guestProfileId` comes only from one visible numeric guest-profile link; missing or ambiguous links yield `null`. No identity is inferred from a display name.
- Reservation details now require a visible sidebar lifecycle heading tied to that code (such as `Past guests`, `Upcoming guests`, `Pending request`, or `Cancelled`) and an explicit `group of N` total reconciled against the Guests section's adult, child and infant labels. The snapshot exposes `status`, `guestCount` and `guestComposition: {adults, children, infants}`. A missing heading, missing count, or mismatched sum fails closed. A heading like `Upcoming guests` is **not** treated as canonical confirmed status or permission to approve a request. One sampled older reservation showed a group total and Guests breakdown that did not reconcile; the strict parser would refuse it. No canonical booking write is made by this pilot.
- Messages use `/hosting/messages`, with visible conversation IDs in `inbox_list_<id>` markers. Read-only local inspection found 15 visible rows, while the header showed 58 unread (not a total-thread count); `#list_inbox` is not scrollable, but an ancestor is. Every visible row must identify exactly one thread. Traversal advances the scrollable ancestor in overlapping steps and fails if it cannot reach a stable end. The selected thread uses `message-thread-container`, `message-list`, `MessageOuterRegistryWrapperSpacingProps`, and `html-rich-text-container`, with no `article` or `data-message-id` contract. A later user-run local reload observed 126 GET and 12 POST requests across `tracking/jitney`, `tracking/airdog`, `api/v2/client_configs`, and `marketing_event_tracking`; temporarily blocking those POST families still left the Messages heading, 15 inbox rows, and 11 thread-panel groups. This supports **visible GET-only hydration for those blocked families**, not full-history completeness, absence of read receipts, blocking every POST, or cloud operation. The extractor deliberately fails closed until stable sender, timestamp, ID and entire-history evidence are established. Opening Messages auto-selected a thread and may mark it read; no claim of zero observable side effects is made.
- The observed Jasmine reload made 159 GET and four first-party POST requests. In a later user-run signed-in personal Chrome check, temporarily blocking the three observed first-party POST families (`tracking/jitney/logging/messages`, `api/v2/client_configs`, `api/v2/marketing_event_tracking`) still left three rendered month grids, 92 date buttons, and 55 reservation bars; the blocker was restored and the tab closed. This is **limited local calendar evidence**, not proof that every POST can be blocked or that Messages works. The pilot still blocks non-GET/HEAD/OPTIONS. For an allowed request it fetches one hop with Playwright `maxRedirects: 0` and **rejects every 3xx response before the browser sees it**. A browser-level synthetic test found that Chromium can follow a fulfilled redirect without a second route callback; refusing all redirects closes that gap. This may prevent the site from rendering. **Signed-in cloud rendering with all POSTs and redirects blocked remains unproven.** Do not relax either boundary without a separate write-risk review and browser-level proof.

All app tests use synthetic guest names, booking codes, profile IDs and page fixtures. A signed-in cloud end-to-end run and real UI read-receipt assessment remain blockers. No local Chrome-cookie transfer is permitted.

## Auth and storage

Snapshots and Playwright storage state use one AES-256-GCM encrypted owner-only file on a 1 GB Fly volume. A failed, partial or expired refresh leaves old evidence unavailable to MCP until a new complete refresh succeeds. Calendar TTL is 15 minutes; Messages TTL is 5 minutes.

The **fresh cloud-login bootstrap code exists but has not been run against Airbnb** and is held by the Terms gate above. If Airbnb later grants the required permission and the other gates are satisfied, a separate HTTP listener could bind `fly-local-6pn:3001`; `fly.toml` maps only port 3000 publicly. It serves a 10-minute, one-at-a-time operator UI with a fresh Playwright context. A localhost egress proxy permits only Airbnb-owned/CDN HTTPS hosts, while a Chromium CDP request-stage gate checks document paths and every redirect request before transmission. All POSTs are denied except exact `AIRBNB_BROWSER_AUTH_POST_URLS` entries: HTTPS URLs on `www.airbnb.co.za`, without query strings, under login/auth/MFA paths, with guest-action paths excluded. There is no wildcard or generic Airbnb-owned POST permission. Unknown real auth endpoints fail closed; blocked POSTs may make login impossible. **No real Airbnb auth POST endpoint has been reviewed, so the list is empty and the viewer stays disabled even if its flag is set.** The main server is also blocked by the separate Terms gate. No live viewer or login viability is claimed.

Third-party SSO paths and detected CAPTCHA iframes stop rather than bypass the session; other challenges are not automated. No browser credentials, OTP, auth state, screenshot or URL query is logged or written to a plaintext file. A 250 ms watcher locks further input as soon as signed-in Hosting navigation is detected, saves `storageState` directly to the encrypted store, and closes the browser; there is no manual Finish action or opportunity to browse other host surfaces after detection. Stop or TTL aborts an in-flight capture; the queued save and encrypted-store commit check cancellation before persistence. A failed or cancelled capture closes without saving. Once an atomic commit has already completed, a later Stop is not retroactive. Refreshes pause during bootstrap; the auth save, refreshes and runtime checkpoints serialize through one service queue so an old state cannot overwrite a fresh login. This is synthetic-test proof, **not** a completed login or evidence that Airbnb's actual MFA path fits the allowlist.

Required runtime settings: `AIRBNB_BROWSER_DATA_KEY` (32 random bytes, base64), `AIRBNB_BROWSER_CALENDAR_URLS` (JSON mapping units `1`-`3` to exact `.co.za/multicalendar/<listingId>` URLs), and **two distinct secrets**: `AIRBNB_BROWSER_MCP_TOKEN` only for `/mcp`, and `AIRBNB_BROWSER_OPERATOR_TOKEN` for operator API and the private bootstrap port. `AIRBNB_BROWSER_BOOTSTRAP_ENABLED=true` requests the private listener only in the pilot Fly runtime; it stays disabled without a JSON array of independently reviewed exact `AIRBNB_BROWSER_AUTH_POST_URLS`. Do not guess or commit actual auth endpoints. Keep actual IDs, credentials and guest data out of Git/logs. `AIRBNB_BROWSER_MESSAGES_URL` defaults to `https://www.airbnb.co.za/hosting/messages`; `AIRBNB_BROWSER_STATE_PATH` defaults to `/data/browser-state.enc`.

**Owner MFA handoff design, dormant until Airbnb's written permission and the other rollout gates are satisfied:**

1. Tristan verifies `/Users/tristdrum/.local/bin/fly-personal auth whoami` and `status --app tristdrum-airbnb-browser-pilot`. Once the app exists, he runs `npm --prefix apps/airbnb-browser run operator:provision` on his Mac. The local helper generates an owner-only `~/.config/airbnb-browser-pilot/operator-token`, runs the same scoped checks, and streams `AIRBNB_BROWSER_OPERATOR_TOKEN` to `fly-personal secrets import --stage` on stdin. It prints no value and uses no token argument. A separate authorized deployment/restart must activate staged secrets and the bootstrap flag; this task does neither.
2. After the auth POST list has been independently reviewed in a separately authorized phase, Tristan runs `npm --prefix apps/airbnb-browser run operator:serve` on his Mac in an interactive TTY. It prompts for a new, strong one-time **local capability** with echo disabled; this is not his Airbnb password or the Fly token. He enters it again in the browser's HTTP Basic prompt (username `operator`). The loopback-only UI proxy uses an ephemeral `127.0.0.1` port printed as a non-secret URL, requires Basic on **every** request, strips Basic before forwarding, and injects the distinct Fly operator bearer only upstream on private `/api` requests. Its tunnel uses `fly-personal proxy <ephemeral-local>:3001 --app tristdrum-airbnb-browser-pilot` over WireGuard. The local proxy and capability expire after 15 minutes. The capability is never displayed, put in a CLI argument or URL, or written to a file; the browser holds only its local Basic-auth cache, not the Fly token. Close the browser tab after use. Port 3001 has no public Fly service mapping; [Fly 6PN binding](https://fly.io/docs/networking/app-services/) and [fly proxy](https://fly.io/docs/flyctl/proxy/) are the transport references.
3. Only Tristan uses the local UI to start one session and enter Airbnb credentials and MFA into its masked local input. The input clears immediately before the private POST is sent; no Codex tool, terminal argument, log, query URL, screenshot file or model prompt contains the values. Signed-in Hosting detection automatically locks, saves encrypted state and closes the session without a Finish click. An unsupported SSO route, detected CAPTCHA iframe, expired 10-minute session, or failed signed-in check ends or rejects the attempt without saving auth. He closes the local proxy process afterward and later disables the bootstrap flag through an authorized change. **Do not paste credentials or OTP into Codex.**

No local Chrome-cookie copy, plaintext auth import, automated login or production session was created here. The private 6PN port is still reachable by other processes in the same Fly private network; the distinct operator token remains mandatory. Exact login/MFA endpoints, live URL policy, MFA usability, browser memory and end-to-end encrypted persistence remain blockers before rollout. The local Basic gate protects the Mac loopback path; it does not prove security against a compromised local user session.

## Availability and cost

`fly.toml` describes **one 1 GB shared-CPU JNB Machine running** with `min_machines_running = 1`, but the runtime Terms gate prevents it from starting. Were Airbnb to grant the required permission, the service design would use internal 5-minute Messages and 15-minute calendar timers; each interval would launch Chromium only for the bounded refresh, then close it. Bootstrap would hold the same queue and pause those refreshes while the human signs in. This is a cost-versus-availability design within the conservative full-month budget reserve, not proof of actual Fly billing or browser memory fit. No app or volume was created.

Public `GET /healthz` is liveness only and includes a `ready` boolean. Operator-only `GET /readyz` represents full pilot readiness; `/readyz/calendar` and `/readyz/messages` expose separate source readiness. The calendar-only `refresh_calendar_before_plan` MCP tool lets cleaner plans use a complete fresh three-listing calendar when Messages still fails closed. Support continues to require complete Messages. No writer is enabled. Operator-only `/metrics` contains no guest data. MCP cannot call operator routes, and the operator token cannot call MCP.

The software gate reserves **US$7.50 per SAST month for a full-month 1 GB shared-CPU Machine** (above the approximate US$6.8 JNB quote), US$1 for one 1 GB volume, up to 4 GB stopped rootfs and snapshots, US$0.50 for the 2 GiB transfer ceiling, and US$0.25 unmetered headroom. That commits US$9.25 before model calls; **Agents API spend is capped at US$0.70/month** through operator-only `/budget/reserve-agent`, leaving US$0.05 margin. It separately tracks actual process-started seconds at US$0.01/hour and transfer at US$0.25/GiB. Runtime checkpoints run every 60 seconds and on shutdown. Browser runs cap at 50 MiB; MCP results cap at 256 KiB. The service makes zero model calls itself.

This is **not an invoice-enforced US$10 cap**. Pre-auth public wakeups, image rootfs size, live region price, extra Machines/volumes/IPs, model calls outside the reservation path, and abrupt-kill time are not independently reconciled. Verify a live JNB quote, image/rootfs and Fly bill, deploy exactly one Machine and volume without a dedicated IP, and add an account-level cap/alert before rollout. [Fly pricing](https://fly.io/docs/about/pricing/) documents running Machine, stopped rootfs and volume billing. No live go-live is authorized until real quote and usage metrics are checked.

## Agents API

Bearer-authenticated `POST /mcp` is a stateless Streamable HTTP MCP endpoint exposing only `get_calendar_snapshot`, `list_message_threads`, `get_message_snapshot`, `refresh_before_plan`, `refresh_calendar_before_plan`, and `get_pilot_status`. No arbitrary model-facing browser executor or Airbnb write tool exists; typed future actions return `READ_ONLY_PILOT`. Guest text is untrusted evidence, not instructions. `agents-adapter.mjs` builds the narrow service-origin HTTP MCP connection with `environment: {type: "none"}`, following the [official Agents API MCP guide](https://developers.openai.com/api/docs/guides/agents-api/tools/mcp) and [environment-none quickstart](https://developers.openai.com/api/docs/guides/agents-api/quickstart). Protocol tests run locally; no OpenAI session was created.

Build context is the repo root; `Dockerfile` pins the official Playwright image to the package version. Future Fly work must use only `/Users/tristdrum/.local/bin/fly-personal` after verifying personal-account identity. This branch authorizes no deployment, login, secret creation or guest communication. Run `npm --prefix apps/airbnb-browser test` for synthetic checks.
